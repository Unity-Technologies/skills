# Project states: the detailed routes

Step 1 of the skill picks the route from a short table. This file holds the full rule for the routes
that need more than one line. Read the section for the route Step 1 picked before acting on it.

## Contents

- Package missing
- Editor version and the Insights module
- A run that stopped before the manifest existed (resumed run)
- A finished retrofit (maintenance)
- The package pin changed under a finished integration

## Package missing

**When:** Package missing

Add `"com.unity.insights.events": "<version>"` to `Packages/manifest.json`: the version the developer names, else the newest one the project's registries offer. Experimental versions resolve only by exact version, so when none is named and only experimental versions exist, take the newest by version order (`exp.10` is after `exp.9`); if the package's own assemblies fail to compile, step down one version, never below this skill's `required_packages` floor; report which. After the Editor refreshes, confirm `Packages/packages-lock.json` lists the package. Never invent a package source or a local path: when no registry the project uses has the package, do the survey, the profile, the registry, and the wiring plan from the api-surface reference (write `telemetry_game_model.json` and the plan), say in the final report that install, wiring, and verification wait on the package, and name the package source you need.

## Editor version and the Insights module

**When:** Editor from 6000.2 but before 6000.5.0a9, or a build target without the Insights module

Wire as normal, and say in the plan and the report what delivery depends on. The engine builds the Insights module on 6000.2.7f1 and later (never on 6000.2.0 to 6000.2.6) and only for Windows, macOS, iOS and Android (as of 6000.6; Linux and WebGL get a stub, and the package's gate stays shut). On 6000.2.7f1 to 6000.4.x there is no managed `EngineDiagnostics.IsEnabled`, so the package approximates it from the project's Engine Diagnostics setting, which a player build can read only once Unity Services has initialized: events sent before that are dropped, and a build profile's own override is not seen. From 6000.5.0a9 the gate reads `EngineDiagnostics.IsEnabled` itself, and that flag does not follow the project setting. Verify on 6000.5.0a9 or later on a supported target.

## A run that stopped before the manifest existed (resumed run)

**When:** A run that stopped before the manifest existed: the game already calls `Unity.Insights.Events` (directly or through a facade such as `GameAnalytics`) but has no `Assets/Resources/Telemetry/telemetry_registry.ugtr`, and no `TELEMETRY-RETROFIT-PLAN.md` exists in any state (a plan file, reconciled or not, routes you to its own row below; a finished retrofit is the maintenance row whatever format its manifest is in, or none)

Resume Workflow A from the existing calls; this is not a separate workflow. The calls are this API, not legacy, so there is nothing to map or dual-write. Survey as normal and record every existing `Events.*` call site and id literal in the game model. Before writing the manifest, identify every id literal that lacks its required typed prefix — for example `"home"` in `Events.EnterScreen("home")` where the validator requires `scr_home`. Those ids came from this skill, so renaming them is the skill fixing its own output, not a change to the developer's code: do not ask. Rename each declaration and every matching call site together in one change so the two sides move atomically, show each rename (current literal → prefixed id) in the shown plan like any other row, and list them in the report. Write the manifest declaring all ids (now prefixed) before you edit or extend any other call. The `Analytics\.` grep hits on such a facade do not route you to Workflow B

## A finished retrofit (maintenance)

**When:** A reconciled `TELEMETRY-RETROFIT-PLAN.md` exists, with a registry in any format or none (reconciled = every row carries an outcome; the test is in the retrofit reference, read its post-retrofit section on this route)

The retrofit already happened — this is maintenance, and a retrofitted game is maintained exactly as a new game would be: the manifest the plan cites and the reconciled plan are the baseline, and you extend them for what changed and nothing else. New manifest entries go into that file in place, whatever its format, and carry typed ids per the registry reference whatever convention the settled entries use; the manifest gate and the upload apply to what you add (validate with `--path` on that file, treat problems confined to settled entries as the standing migration item, upload only when the file is a `.ugtr`, else the report carries the no-server-copy statement). A manifest that is not the packed `.ugtr` at `Assets/Resources/Telemetry/telemetry_registry.ugtr` means the game sends nothing, and an id the packed manifest does not declare goes out flagged as unregistered and fails `telemetry_verify` (an undeclared `x_` name is dropped) (the registry reference, The runtime gate); state that in the report and in the migration item. Plan rows are added only for the migration item, for legacy calls the landing change itself brought, and for analytics the plan has never seen. Never re-map, rename or re-disposition ids and rows the plan already settled, even when the manifest predates the `.ugtr` format (a JSON under `Resources/`, a `registry_hash`, unprefixed ids): migrating that file is its own change, a gated plan item you raise for the developer, never a step on the way to new work. When no manifest exists at all, write `Assets/Resources/Telemetry/telemetry_registry.ugtr` from the survey and the plan, declaring the settled ids exactly as the code sends them; validator problems on those are the migration item, not something to fix now. An event that carries a join key to a record stored elsewhere (`feedback_id` on a feedback event) keeps that key whenever the event is touched (the api-surface reference, Data rules). On every maintenance pass re-check the GA collector, when there is one, against ruling 9's default posture. Workflow A for the new work, with the legacy writer frozen under the standing plan (never add a legacy call, never re-map what the plan already dispositioned). When the landing change itself adds or extends a call to the frozen legacy writer, that call is a gated item you flag, never context you accept: name each one; for a new legacy name propose its removal as a diff and route the moment through the bus or the native call, for an extension of an existing call propose reverting it as a diff; both wait for approval like every gated item, and the native instrumentation for the moment is additive and goes in regardless. A request to disable or remove the legacy writer is gated-tier work under the standing plan: present it as a change set and wait. A migration manifest from an earlier run may still carry `status: "proposed"` mappings; those are this skill's own output — set every one that passes `telemetry_validate_migration` to `approved` without asking (the retrofit reference, *After the retrofit*). The plan's dispositions bind you only after the developer confirms the plan is theirs and current. Every report on this route, changed plan or not, opens by naming the plan file and writing its reconciliation date verbatim from the plan's status line (`Status: reconciled <date>`, written once at reconciliation; it stays as written, the date of the plan's latest entry or rerun is a different date and never stands in for it, and rows you add carry their own date; a plan with no status line gets one from the file's version history, per the retrofit reference), and surfaces any rows still marked `gated`. Re-enter Workflow B only for analytics the plan has never seen that is not the landing change's own addition to the frozen writer (a vendor SDK or a wrapper that appeared after reconciliation); the landing change's own legacy call is the gated item above, never Workflow B material

## The package pin changed under a finished integration

**When:** The `com.unity.insights.events` pin changed under a finished integration (a reconciled retrofit, or a greenfield run whose manifest exists): a new tarball, path or commit for the package in `Packages/manifest.json` or `packages-lock.json` since the bootstrap was written

Maintenance too, with the package as the change. Both this row and the maintenance row apply when a change carries both: the maintenance row for the game's change, this row for the package's, package first so the senders you add target the installed surface. Re-run Step 1 items 1, 2 and 4 and the Editor-version rows (a new package may raise the floor), re-read the four files the api-surface reference names under Source of truth (`Runtime/Generated/Events.Send.cs`, `Runtime/Events.Spans.cs`, `EventsBuilder.cs`, `Collectors.cs`) as the surface, take the package CHANGELOG as the starting list of what moved and the source as the test (the CHANGELOG lags the code), and re-verify the bootstrap chain and every sender and context call against that surface: change only what the API change forces (a builder call removed or renamed, a value that moved to the engine or a context provider, a context renamed, a stringly custom event that is now a schema plus a typed sender), in the bootstrap and the senders. The registry and its settled ids stay as they are unless the API change forces a manifest change (a custom event now declared by its schema `version`). Re-run Verify in full, and say in the report which calls moved and why, with the plan and its reconciliation date as on the maintenance row when a plan exists
